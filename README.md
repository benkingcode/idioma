# Idioma

**AI-first, compile-time i18n for React. Write in English, ship in every language.**

**Each page ships only the translations it uses.** Every message is compiled into the component that renders it, so your bundler's code splitting splits your translations too, with nothing to configure. See [Automatic Code Splitting](#automatic-code-splitting).

About 1.4 KB of runtime. Automatic key generation. AI-powered translation that understands your codebase and key context.

Traditional i18n workflow: Write code → Extract messages → Upload to TMS → Wait for translators → Download → Test → Find bugs → Repeat.

With Idioma: Write code → Run `idioma translate` → Ship.

```bash
# Translate all missing messages with AI
idioma translate

# Extracting messages from source files...
# Generating context from source code...
# Translating 847 messages to es...
# ✓ Done in 12.3s
```

Idioma reads your source code to understand context ("checkout button", "error message in cart"), then translates with that understanding. No more uploading CSVs or waiting for translators on routine updates.

## Features

**Performance**

- **Automatic code splitting**: Each page ships only the translations its components use, with no namespaces to set up and no catalogues to load
- **About 1.4 KB of runtime**: Translations are inlined at build time; the runtime just renders them
- **Compile-time processing**: No runtime parsing or fetching

**Developer Experience**

- **Write natural JSX**: `<Trans>Hello {name}</Trans>`, not `t('greeting.hello', {name})`
- **Flexible key strategy**: Auto-generated keys for rapid development; explicit IDs when you need stable, refactor-proof translations
- **AI-powered translation**: Built-in translation with any AI SDK model (Claude, GPT, Gemini and others), with translator context read from your code
- **Type-safe**: Generated TypeScript types message keys and required values (forget `{name}` and TypeScript tells you)
- **ICU MessageFormat**: Full support for plurals, selects, ordinals, and complex formatting

**Integrations**

- **Vite plugin**: HMR for translations, zero config
- **React Native / Metro**: First-class React Native support with Metro bundler
- **React Server Components**: Compile-time inlined translations work seamlessly in RSC
- **PO file format**: Works with Phrase, Lokalise, Crowdin, and any TMS
- **Plain JS support**: `createT` for Zod schemas, error handling, and non-React code

## Quick Start

Requirements: Node 22 or later, React 18 or 19 (Suspense mode needs 19), and Vite 8 or later for the web or Metro for React Native.

```bash
npm install @idioma/core @idioma/react
```

Add the Vite plugin:

```ts
// vite.config.ts
import idioma from '@idioma/core/vite';
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react(), idioma()],
});
```

The plugin needs Vite 8 or later. It transforms each module with Oxc in its own `pre` transform, before `@vitejs/plugin-react` sees it, so it works with plugin-react 6 and its React Compiler (`react({ compiler: true })`). It needs no Babel.

Create a config file:

```ts
// idioma.config.ts
import { defineConfig } from '@idioma/core';

export default defineConfig({
  idiomaDir: './src/idioma',
  defaultLocale: 'en',
  locales: ['en', 'es', 'fr'],
});
```

This creates a folder structure:

```
src/idioma/
├── locales/      # PO files (git tracked)
├── index.ts      # Trans, useT, etc. (typed wrapper)
├── plain.ts      # createT (non-React)
└── .generated/   # Internal files (gitignored)
```

Set up a path alias for clean imports:

```json
// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "@/idioma": ["./src/idioma"],
      "@/idioma/*": ["./src/idioma/*"]
    }
  }
}
```

Set up the provider:

```tsx
// main.tsx
import { IdiomaProvider } from '@/idioma';

createRoot(document.getElementById('root')!).render(
  <IdiomaProvider locale="en">
    <App />
  </IdiomaProvider>,
);
```

Use it:

```tsx
import { Trans } from '@/idioma';

function Greeting({ name }) {
  return <Trans>Hello {name}!</Trans>;
}
```

### Why import from generated code?

Idioma generates a thin typed wrapper in your project. This gives you full autocomplete on message IDs, locales, and namespaces without macro magic:

```ts
// Auto-generated by @idioma/core
import { createTrans, createUseT } from '@idioma/react';
import type { IdiomaTypes } from './.generated/types';

export const Trans = createTrans<IdiomaTypes>();
export const useT = createUseT<IdiomaTypes>();
```

The `IdiomaTypes` generic carries your actual message keys through to the components, so `<Trans id="...">` autocompletes with your real messages.

## Automatic Code Splitting

Each page ships only the translations its components use, with nothing to configure. Most i18n libraries load a whole catalogue per locale, or the namespaces you split it into by hand. Idioma compiles every message into the component that renders it, so your bundler's own code splitting decides which page gets which strings.

**How it works:**

1. At build time, the transform replaces each `<Trans>` and `t()` call with the message it renders, inlined at the call site
2. Each message travels with its component's code, into whichever chunk the bundler puts that component in
3. Route-level and lazy splitting therefore split your translations too: a page loads only the chunks it needs, and their messages with them

A 10,000-message app doesn't ship 10,000 messages to every page: each page gets only what it needs.

**What gets bundled:**

- ✅ Translations for components rendered on the page
- ❌ Translations for components on other routes

By default each message carries every locale, so switching locale is instant. For apps where initial bundle size is critical, [Suspense mode](#suspense-mode-react-19) loads only the active locale.

## React Native

Add the Metro configuration wrapper:

```js
// metro.config.js
const { getDefaultConfig, mergeConfig } = require('@react-native/metro-config');
const { withIdioma } = require('@idioma/core/metro');

const config = getDefaultConfig(__dirname);

module.exports = withIdioma({
  idiomaDir: './src/idioma',
  defaultLocale: 'en',
})(config);
```

There is no Babel plugin to add. `withIdioma` sets Metro's `babelTransformerPath` to Idioma's transformer, which transforms each module with Oxc and then hands it to your app's own transformer (Expo's or React Native's), so `babel.config.js` stays as it is. If your config already sets a custom `babelTransformerPath`, Idioma wraps that one.

Set up the provider in your app root:

```tsx
// App.tsx
import { IdiomaProvider } from '@/idioma';

export default function App() {
  return (
    <IdiomaProvider locale="en">
      <Main />
    </IdiomaProvider>
  );
}
```

Use translations in your components:

```tsx
import { Trans, useT } from '@/idioma';
import { Text, View } from 'react-native';

function Greeting({ name }) {
  const t = useT();
  return (
    <View>
      <Text>
        <Trans>Hello {name}!</Trans>
      </Text>
      <Text>{t('Welcome to the app')}</Text>
    </View>
  );
}
```

The Metro plugin automatically compiles translations on startup and watches for PO file changes during development. Translations are inlined into each module, and Metro caches transformed modules, so restart Metro to see a PO edit in the app.

> **Tip:** To use `@/idioma` imports in React Native, add [babel-plugin-module-resolver](https://github.com/tleunen/babel-plugin-module-resolver) to your Babel config.

**Note:** Idioma compiles translations at build time. For OTA translation updates without app store releases, you'll need to integrate with a service like Expo Updates or CodePush and rebuild the JS bundle.

## React Server Components

For translations in React Server Components, use `createT` from the plain module:

```tsx
// Page.tsx (Server Component)
import { createT, type Locale } from '@/idioma/plain';

export default async function Page({ locale }: { locale: Locale }) {
  const t = createT(locale);

  return (
    <div>
      <h1>{t('Welcome to our app')}</h1>
      <p>{t('Hello {name}', { name: 'Ben' })}</p>
    </div>
  );
}
```

The `t` function is synchronous—translations are compiled into the bundle at build time, so there's no runtime fetching. This makes RSC usage straightforward: just call `createT` with the locale and use it.

```ts
// Source text (auto-hashed to key)
t('Hello world!');

// With values (2nd arg)
t('Hello {name}', { name: 'Ben' });

// Key-only mode (like <Trans id="...">)
t({ id: 'welcome' });
t({ id: 'greeting', source: 'Hello {name}', values: { name: 'Ben' } });
```

The client-side `useT` hook uses the same API, so you can share translation patterns between server and client components.

## Plain JavaScript (Outside React)

For translations in utility functions, validation schemas, error messages, or any code outside React components, use `createT`:

```typescript
// utils/validation.ts
import { createT, type Locale } from '@/idioma/plain';

export function createUserSchema(locale: Locale) {
  const t = createT(locale);

  return z.object({
    email: z.string().email(t('Invalid email address')),
    password: z
      .string()
      .min(8, t('Password must be at least {min} characters', { min: 8 })),
  });
}

// Usage
const schema = createUserSchema('es');
schema.parse(formData); // Errors in Spanish
```

Works great for:

- **Zod/Yup schemas** — Localized validation messages
- **Error handling** — Translated error classes
- **Utility functions** — Any non-React code that needs i18n
- **Constants** — Lazy-evaluated translated labels

```typescript
// Translated errors
import { createT, type Locale } from '@/idioma/plain';

type ErrorCode = 'notFound' | 'forbidden';

// Each id is a literal, so the build can inline it
export function errorMessage(code: ErrorCode, locale: Locale) {
  const t = createT(locale);
  switch (code) {
    case 'notFound':
      return t({ id: 'errors.notFound' });
    case 'forbidden':
      return t({ id: 'errors.forbidden' });
  }
}

export class AppError extends Error {
  constructor(code: ErrorCode, locale: Locale) {
    super(errorMessage(code, locale));
    this.name = 'AppError';
  }
}
```

**Static and dynamic strings:** a call with a literal string or id is inlined at build time, so its translations ship with the code that uses it. A string known only at runtime, `t(message)`, is not translated: it renders as written. To choose a message at runtime, pick between literal ids, with a `switch` as above or a conditional: `t({ id: live ? 'set.live' : 'set.past' })`.

## Usage

### Basic translation

```tsx
<Trans>Welcome to our app</Trans>
```

### Variable interpolation

```tsx

```

### Component interpolation

```tsx
<Trans>

  <Link to="/privacy">privacy policy</Link>

```

### Explicit keys

Use explicit IDs for translations that need to survive source text refactoring:

```tsx
// ID-only (translation comes entirely from PO file)
<Trans id="welcome.hero" />
<Trans id="greeting" values={{ name: 'Ben' }} />

// Hybrid: stable ID + fallback content if translation is missing
<Trans id="checkout.confirm">Confirm Order</Trans>
```

This is useful for checkout flows, legal text, or any message that goes through formal translation review. See [Choosing Your Key Strategy](#choosing-your-key-strategy) for guidance.

What extraction writes for an explicit id depends on whether the call carries its text:

| Call                                                     | Default locale's `msgstr` | Other locales' `msgstr` |
| -------------------------------------------------------- | ------------------------- | ----------------------- |
| `<Trans id="checkout.confirm">Confirm order</Trans>`     | `Confirm order`           | empty, to translate     |
| `t({ id: 'checkout.confirm', source: 'Confirm order' })` | `Confirm order`           | empty, to translate     |
| `t({ id: 'checkout.nameLabel' })`                        | **empty**                 | empty, to translate     |

A key-only call has no text to extract, so you write its default-locale text in that locale's PO file yourself. Until then it renders its id in every locale that lacks a translation.

### Static ids (checked at build time)

Idioma inlines translations at build time, so an id must be known at build time. A call it cannot inline would render the id itself, so **the build fails** instead, with a code frame pointing at the call:

```tsx
// ✅ A string literal
t({ id: 'set.title' });
<Trans id="set.title" />;

// ✅ A conditional of string literals: compiles to one call per branch
t({ id: live ? 'set.live' : 'set.past' });
<Trans id={live ? 'set.live' : 'set.past'} />;

// ❌ Fails the build: the id is only known at runtime
t({ id: key });
<Trans id={key} />;
```

`t` must come from `useT()` or `createT()` in the same file as the call. Passing `t` into a helper fails the build when the helper uses a key from your catalogue; pass the locale instead and call `createT` inside the helper:

```ts
// ❌ Fails the build
function describe(t: ReturnType<typeof createT>) {
  return t({ id: 'set.title' });
}

// ✅
function describe(locale: string) {
  const t = createT(locale);
  return t({ id: 'set.title' });
}
```

`Trans` must be imported from your generated idioma module, not from `@idioma/react`. A dynamic source string, `t(message)`, still compiles, but it is not translated: it renders as written.

### What fails the build

Idioma fails the build, with a message that names the file, rather than ship text that would render wrong:

| Fails the build                                                                                   | Why                                            |
| ------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `t({ id })` or `<Trans id>` whose id is not a string literal or a conditional of them             | It can't be inlined, so it would render its id |
| `t({ id: 'a.key' })` on a function that isn't a `t` from `useT()` or `createT()` in the same file | Same: it is never inlined                      |
| `<Trans id>` that isn't imported from your idioma folder                                          | Same                                           |
| A PO file that does not parse                                                                     | Its whole locale would be missing              |
| A plural, select or selectordinal in a PO file that is not valid ICU MessageFormat                | The page would show the raw ICU                |

The first three are code errors: the dev server shows them too, at the call. The last two are catalogue errors: the dev server logs them and keeps running, so a half-edited PO file doesn't stop it.

The second check looks at any call with `{ id: '...' }` whose id is in your catalogue, whatever the function, so `router.navigate({ id: 'settings' })` fails if `settings` is also a message id. Dotted ids such as `settings.title` keep the two apart.

### Context

Add translator context that affects key generation (same text, different context = different key):

```tsx
<Trans context="button">Submit</Trans>
<Trans context="form.title">Submit</Trans>
```

### Pluralization

Use the `plural()` function inside `<Trans>` for pluralization:

```tsx
import { Trans } from '@/idioma';
import { plural } from '@idioma/core/icu';

<Trans>
  You have {plural(count, { one: '# item', other: '# items' })} in your cart
</Trans>;
```

The `#` placeholder is replaced with the numeric value. This compiles to ICU MessageFormat:

```
You have {count, plural, one {# item} other {# items}} in your cart
```

In `t()`, write the ICU message itself, in `source` or in the PO file. `plural()`, `select()` and `selectOrdinal()` inside a `t()` template literal are not supported yet: such a call is never translated.

```tsx
const t = useT();
t({
  id: 'cart.count',
  source: 'You have {count, plural, one {# item} other {# items}} in your cart',
  values: { count },
});
```

Full plural forms for different languages:

```tsx
plural(count, {
  zero: 'No items', // 0 items (some languages)
  one: '# item', // 1 item
  two: '# items', // 2 items (Arabic, Welsh)
  few: '# items', // 2-4 items (Slavic languages)
  many: '# items', // 5+ items (Slavic, Arabic)
  other: '# items', // Required fallback
});
```

### Selection

Use the `select()` function for exact value matching (gender, status, categories):

```tsx
import { Trans } from '@/idioma';
import { select } from '@idioma/core/icu';

<Trans>
  {select(gender, { male: 'He', female: 'She', other: 'They' })} liked your post
</Trans>;
```

This compiles to ICU MessageFormat:

```
{gender, select, male {He} female {She} other {They}} liked your post
```

The `other` form is required as a fallback for unmatched values.

### Ordinal Numbers

Use `selectOrdinal()` for ordinal formatting (1st, 2nd, 3rd):

```tsx
import { Trans } from '@/idioma';
import { selectOrdinal } from '@idioma/core/icu';

<Trans>
  You finished in{' '}
  {selectOrdinal(place, { one: '#st', two: '#nd', few: '#rd', other: '#th' })}{' '}
  place
</Trans>;
```

The `#` placeholder is replaced with the numeric value. This compiles to ICU MessageFormat:

```
You finished in {place, selectordinal, one {#st} two {#nd} few {#rd} other {#th}} place
```

Ordinal rules are locale-aware via CLDR. In English:

- `one` = 1, 21, 31... (ends in 1, not 11)
- `two` = 2, 22, 32... (ends in 2, not 12)
- `few` = 3, 23, 33... (ends in 3, not 13)
- `other` = 4, 5, 11, 12, 13, 14...

### Number and Date Formatting

For number, currency, and date formatting, use the standard `Intl` APIs alongside Idioma:

```tsx
import { Trans, useLocale } from '@/idioma';

function Price({ amount }) {
  const locale = useLocale();
  const formatted = new Intl.NumberFormat(locale, {
    style: 'currency',
    currency: 'EUR',
  }).format(amount);

  return <Trans>Total: {formatted}</Trans>;
}

function EventDate({ date }) {
  const locale = useLocale();
  const formatted = new Intl.DateTimeFormat(locale, {
    dateStyle: 'long',
  }).format(date);

  return <Trans>Event on {formatted}</Trans>;
}
```

Idioma focuses on message translation and delegates formatting to the platform's `Intl` APIs, which handle locale-specific number, currency, and date formatting natively.

### Imperative usage with useT

```tsx
import { useT } from '@/idioma';

function SearchInput() {
  const t = useT();
  return <input placeholder={t('Search...')} />;
}

function Greeting({ name }) {
  const t = useT();

  // With values (2nd arg)
  const greeting = t('Hello {name}', { name });

  // With an explicit id
  const submitLabel = t({ id: 'form.submit', source: 'Submit' });

  return <span>{greeting}</span>;
}
```

A third argument, `t('Submit', undefined, { context: 'button' })` or `{ ns: 'common' }`, is not supported yet: the call compiles as if it were not there. To tell apart two uses of the same text, give each its own id. For a namespace, use `t({ id, ns })`.

### useLocale

Get the current locale:

```tsx
import { useLocale } from '@/idioma';

function LanguageSwitcher() {
  const locale = useLocale();
  return <span>Current: {locale}</span>;
}
```

### Namespaces

Organize translations into namespaces for large apps:

```tsx
// In components
<Trans ns="marketing">Welcome to our platform</Trans>;

// With useT: the object form takes ns
const t = useT();
t({ id: 'subscribe', source: 'Subscribe now', ns: 'marketing' });
```

A namespace's messages live in `locales/{locale}/{namespace}.po`, for example `locales/es/marketing.po`.

### translate

AI-powered translation with any [AI SDK](https://ai-sdk.dev/providers) model, set as `ai.model` in `idioma.config.ts` (see [Configuration](#configuration)). The provider reads its API key from the environment, for example `ANTHROPIC_API_KEY`.

Idioma uses AI SDK 6, so install a version 3 provider, such as `pnpm add -D @ai-sdk/anthropic@3`. Version 4 providers are built for AI SDK 7, and AI SDK 6 rejects their models.

```bash
idioma translate                    # Translate missing messages
idioma translate --force            # Retranslate all messages
idioma translate --dry-run          # Run without API calls or saving
idioma translate --verbose          # Show AI prompts and responses
idioma translate --no-auto-context  # Skip automatic context generation
```

**How it works:**

1. **Guidelines:** Configure `ai.guidelines` to describe your app's tone, audience, and style. These guidelines are sent to the AI during both context generation and translation, ensuring consistent results across your entire app.

2. **Context generation:** Idioma reads your source files and uses AI to generate translator context for each message (e.g., "Button label in checkout form", "Error shown when payment fails"). This context is saved to the PO file.

3. **Translation:** The AI translates each message using the generated context and your project guidelines, producing more accurate results than context-free translation.

```po
#. [AI Context]: Button label shown when user confirms their order
#: src/components/Checkout.tsx
msgid "checkout.confirm"
msgstr "Confirmar"
```

**Cost and performance:** Translation uses batched API calls. A typical 1,000-message project costs roughly $0.50 to $2.00, depending on message complexity and provider. Context generation is a one-time cost per message; subsequent translations reuse existing context.

**Dry run mode:** The `--dry-run` flag runs the translation pipeline without making API calls or saving files. Combined with `--verbose`, you can inspect the exact prompts that would be sent to the AI. That helps when you debug your guidelines or want to see what context each message receives:

```bash
idioma translate --dry-run --verbose
```

**Review workflow:** Translations are written to standard PO files that can be committed and reviewed in your normal PR process, or synced to a TMS like Phrase, Lokalise, or Crowdin for professional review.

## Configuration

```ts
// idioma.config.ts
import { defineConfig } from '@idioma/core';

export default defineConfig({
  // Base directory for all Idioma files
  // Generated files go in {idiomaDir}/, PO files in {idiomaDir}/locales/ by default
  idiomaDir: './src/idioma',

  // Optional: Override PO file location if you have existing translations elsewhere
  // localesDir: './locales',

  // Source language
  defaultLocale: 'en',

  // Target languages
  locales: ['en', 'es', 'fr', 'de', 'ja'],

  // Enable Suspense-based lazy loading (React 19+)
  useSuspense: false,

  // Files to scan for messages (default: ['**/*.tsx', '**/*.jsx', '**/*.ts', '**/*.js'])
  sourcePatterns: ['src/**/*.tsx', 'src/**/*.jsx'],

  // PO file output: keep each string on one line (default: fold at 76 columns)
  po: { foldLength: 0 },

  // AI translation config (uses Vercel AI SDK)
  // Install a provider built for AI SDK 6: pnpm add -D @ai-sdk/anthropic@3
  ai: {
    model: anthropic('claude-sonnet-5-5'), // import { anthropic } from '@ai-sdk/anthropic'
    // See https://ai-sdk.dev/providers for other providers (openai, google, etc.)

    // Project-specific guidelines for AI translation
    guidelines: `This is a children's educational game for ages 4-8.
Use simple, friendly language. Avoid complex vocabulary.`,
  },
});
```

## Locale Fallbacks

When a translation is missing, Idioma follows a fallback chain:

1. **Exact locale** (`es-MX`)
2. **Base locale** (`es` from `es-MX`)
3. **Default locale** (`en`)
4. **Source text**, or the id of a key-only message

It never shows another locale's translation: a key with no default-locale text renders its id on every locale that lacks it, so the gap is visible instead of showing, say, Catalan on an English page.

## Content-Addressable Keys

Idioma uses content-addressable keys—the message text determines the key:

1. **Murmurhash3** generates a 32-bit hash from the source message
2. **Base62 encoding** (0-9, A-Z, a-z) produces compact 8-character keys
3. Keys are **deterministic**: same input always produces the same key

```
"Hello {name}" → murmurhash3 → base62 → "a7Fk29xQ"
```

The `context` prop creates different keys for identical text:

```tsx
<Trans>Submit</Trans>                        // → "xK9mP2nL"
<Trans context="button">Submit</Trans>       // → "r4Yt8wQz" (different key)
```

### Choosing Your Key Strategy

Auto-generated keys are convenient but change when source text changes. Explicit IDs are stable across refactoring. Choose based on your needs:

| Strategy         | Syntax                                               | Best for                                         |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------ |
| **Auto keys**    | `<Trans>Confirm Order</Trans>`                       | Rapid iteration; AI retranslation is cheap       |
| **Explicit IDs** | `<Trans id="checkout.confirm" />`                    | Critical UI, legal text, formal review workflows |
| **Hybrid**       | `<Trans id="checkout.confirm">Confirm Order</Trans>` | Stable key + readable fallback                   |

Most teams use auto keys by default and explicit IDs for checkout flows, legal text, or anything requiring formal translation review.

## PO File Format

Idioma uses the standard [gettext PO format](https://www.gnu.org/software/gettext/manual/html_node/PO-Files.html), one file per locale, with ICU MessageFormat in translations. The files are key-based: each `msgid` is the message's id, or its 8-character key when it has none, and the default locale's file holds the source text as its `msgstr`.

```po
# locales/en.po: the default locale holds the source text

#: src/components/Checkout.tsx
#, extracted
msgid "checkout.confirm"
msgstr "Confirm order"

# An auto-keyed message (<Trans>Hello, {name}!</Trans>): its msgid is its key
#: src/components/Greeting.tsx
#, extracted
msgid "0024c34D"
msgstr "Hello, {name}!"
```

```po
# locales/es.po

msgid "checkout.confirm"
msgstr "Confirmar pedido"

msgid "0024c34D"
msgstr "¡Hola, {name}!"

# With context (from <Trans context="button">): part of the key, and kept as msgctxt for translators
msgctxt "button"
msgid "001CDU6P"
msgstr "Enviar"

# Pluralization (ICU format)
msgid "cart.count"
msgstr "{count, plural, one {# artículo} other {# artículos}}"

# Component interpolation (tag names from JSX)
msgid "legal.links"
msgstr "Lee nuestros <Link>términos de servicio</Link> y <Link>política de privacidad</Link>"
```

Because a translation file holds keys, not source text, upload the default locale's file as the source language when you send catalogues to a translation management system such as Phrase, Lokalise or Crowdin.

Idioma rewrites a PO file only when its messages change, so hand edits and TMS formatting survive dev-mode saves. When a file is written, lines longer than 76 columns are folded. Set `po: { foldLength: 0 }` to keep each string on one line, for example to match your TMS export. The Metro plugin doesn't read `idioma.config.ts`, so pass the same `po` option to its `withIdioma()`.

## Suspense Mode (React 19+)

For apps where initial load size is critical, Suspense mode takes optimization further: instead of bundling all locale variants, it loads only the active locale via dynamic imports.

```ts
// idioma.config.ts
export default defineConfig({
  idiomaDir: './src/idioma',
  defaultLocale: 'en',
  locales: ['en', 'es', 'fr'],
  useSuspense: true, // Enable lazy loading
});
```

Wrap your app with a Suspense boundary:

```tsx
import { IdiomaProvider } from '@/idioma';

<IdiomaProvider locale={locale}>
  <Suspense fallback={<Loading />}>
    <App />
  </Suspense>
</IdiomaProvider>;
```

**Trade-offs:**

|                      | Default mode           | Suspense mode          |
| -------------------- | ---------------------- | ---------------------- |
| Translations bundled | Per-page (tree-shaken) | Per-page (tree-shaken) |
| Locales bundled      | All locales            | Active locale only     |
| Locale switch        | Instant                | Suspends until loaded  |
| React version        | 18+                    | 19+ (uses `use` hook)  |

## API Reference

### Trans Component

| Prop         | Type                      | Description                                    |
| ------------ | ------------------------- | ---------------------------------------------- |
| `children`   | `ReactNode`               | Message content with interpolations            |
| `id`         | `string`                  | Explicit message key (alternative to children) |
| `context`    | `string`                  | Translator context (affects key generation)    |
| `ns`         | `string`                  | Namespace for organizing translations          |
| `values`     | `Record<string, unknown>` | Values for placeholder interpolation           |
| `components` | `ReactNode[]`             | Components for tag interpolation               |

```tsx
// Children-based (auto-keyed)
<Trans>Hello {name}</Trans>
<Trans context="button">Submit</Trans>

// ID-based (explicit key)
<Trans id="welcome.hero" />
<Trans id="greeting" values={{ name: 'Ben' }} />

// Hybrid (stable key + fallback content)
<Trans id="checkout.confirm">Confirm Order</Trans>
```

### useT Hook

```ts
const t = useT();

// Basic usage
t('Hello world'); // Simple message
t('Hello {name}', { name: 'Ben' }); // With values

// ID-based
t({ id: 'welcome' }); // Key only (translation must exist in PO)
t({ id: 'greeting', source: 'Hello {name}', values: { name: 'Ben' } }); // With source text + values
t({ id: 'save', ns: 'common' }); // In a namespace
```

The `source` field provides default locale text for extraction (like children in `<Trans id="...">Source text</Trans>`). Without `source`, the PO entry gets an empty `msgstr` and you must add translations manually.

### createT (Plain JS)

```ts
import { createT } from '@/idioma/plain';

const t = createT('es'); // Create for specific locale

// Same API as useT
t('Hello world');
t('Hello {name}', { name: 'Ben' });
t({ id: 'welcome' });
t({ id: 'greeting', source: 'Hello {name}', values: { name: 'Ben' } });
```

### ICU Helpers

```ts
import { plural, select, selectOrdinal } from '@idioma/core/icu';

// Pluralization
plural(count, { one: '# item', other: '# items' });

// Selection
select(gender, { male: 'He', female: 'She', other: 'They' });

// Ordinals
selectOrdinal(place, { one: '#st', two: '#nd', few: '#rd', other: '#th' });
```

### IdiomaProvider

```tsx
import { IdiomaProvider, useLocale } from '@/idioma';

<IdiomaProvider locale="en">
  <App />
</IdiomaProvider>;

// Get current locale
const locale = useLocale(); // 'en'
```

## How It Works

In development and in the production build alike, the Vite plugin (or the Metro transformer) compiles each module before React sees it:

```
<Trans>Hello {name}</Trans>
    ↓
<__Trans __t={{ en: "Hello {name}", es: "Hola {name}", __source: "Hello {name}" }} __a={{ name }} />
```

`__t` holds this one message in every locale, and `__a` its values. At runtime, `__Trans` picks the active locale's text and fills in the values. A `t()` call is compiled the same way, with the translations as its second argument.

The transform is built on the Oxc parser. It generates content-addressed keys for messages without an id and inlines each message's compiled translations where it is used. In development, saving a file also extracts its messages into the PO files and recompiles them.

## Editor Support

TypeScript provides full type safety via generated types:

- **Required values** — Type errors when you forget interpolation values (`t('Hello {name}')` requires `{ name: string }`)
- **Locales** — Autocomplete and validation on locale strings
